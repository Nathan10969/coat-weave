CORE EXTRACTION RULES
=====================

0. **Stage 7A -> 7B -> 7C -> 7D contract.**
   First create ``extraction_plan`` (7A): identify table/figure type, whether
   samples are rows or columns, sample ids, expected formulation facts,
   expected performance facts, and mandatory context fields that the ledger
   shows must be bound. Then extract (7B): emit sample_map, context_assertions,
   facts, cell_annotations, and coverage_audit. The pipeline will validate
   coverage/schema/evidence binding (7C). If validation fails, the repair call
   (7D) will ask you to return a COMPLETE corrected JSON object, not a patch.

   Validation-sensitive rule: if the ledger/table contains result or
   formulation cells, do not return zero facts. If expected_result_cells > 0
   and facts is empty, the unit is blocked and must be repaired. If the ledger
   shows substrate/process/test_standard evidence, emit it either directly on
   the fact or as a context_assertions record with source_ledger_ids. Schema
   quirks such as resin_system list, process string/list/dict, standard_id vs
   test_standard, substrate string, and qualitative values like
   >100/100*/100**/OK/pass/fail/rating are allowed; keep the value text and let
   the deterministic normalizer coerce shape. Do not omit the fact to avoid a
   schema problem.

1. **Evidence rule.** Every fact/assertion must cite source evidence through
   ``source_ledger_ids`` or ``evidence_pointer``. For table/figure units, result
   values normally come from table cells, figure labels, captions, or footnotes.
   The EVIDENCE LEDGER can also support prose facts when the paragraph itself
   reports a measured result, formulation amount, preparation condition, sample
   identity, test standard, or test condition. Do not invent context that is not
   in the ledger.

1a. **Ledger-driven sample/context extraction.**
   Use the EVIDENCE LEDGER to extract:
     - sample_map: sample/example/control/comparative identities and aliases.
     - context_assertions: substrate, process, film thickness, cure condition,
       test method, exact standard, preparation, and sample-scoped context.
     - facts: measured results and formulation quantities bound to the correct
       sample/test/table paragraph.
   If a context assertion cannot be bound to a sample, emit it with
   target_scope="unit" or "document"; do NOT attach it to all samples by guess.
   If a fact cannot be bound to a sample, keep example_id null and add a
   coverage_audit unresolved_bindings entry. Never collapse unresolved facts
   into a global "unknown" sample.

   Context completeness is mandatory. When row/column/caption/ledger identifies a tested substrate
   or panel, write a per-fact substrate when it
   varies by row/column, or emit a context_assertions substrate when it is
   shared by the table/unit/sample. Do not leave substrate unknown when the
   table row says "iron phosphate-treated panel", "aged polyurethane panel",
   "wood", "steel", "metal", "plastic", or equivalent.

   Process completeness is mandatory too. Extract application/preparation
   steps such as CED/electrodeposition, spray, drawdown, lamination,
   printing/jetting/NIR, thermal cure, ambient cure, UV cure, mixing,
   dispersion, bake temperature, cure time, and pretreatment. Put sample- or
   row-specific process directly on the fact; put shared process in
   context_assertions. This applies to formulation tables as well as
   performance tables.

   Resolve evidence conflicts by trusting patent prose, captions, footnotes,
   and exact standards over speculative VLM summaries. If the ledger prose says
   MEK double rub, ASTM D5402 / ASTM D 5402-15, methyl ethyl ketone, or
   solvent resistance, extract a chemical-resistance/solvent-resistance fact
   with TEST_MEK_rub and the exact standard in test_condition. It is not mar/scratch/mechanical
   even if a table summary calls it "cure performance".

1b. **Cell role first, then fact extraction.**
   Before emitting facts, classify each meaningful table cell/row/column into
   exactly one semantic role:

     RESULT_PROPERTY      = measured outcome, evaluation result, rating, score,
                            pass/fail, yield, particle size, adhesion, gloss,
                            haze, corrosion, scribe creep, blistering, flame
                            test result, scratch, contact angle, MEK rubs, etc.
     FORMULATION_QUANTITY = material amount, wt%, pbw, phr, ratio, component
                            dosage, feed composition, resin/additive quantity
                            when the table/prose defines a sample recipe or
                            formulation composition.
     FORMULATION_CONTEXT  = shared formulation description that helps interpret
                            a RESULT_PROPERTY fact but is not itself a sample
                            recipe cell.
     PROCESS_CONDITION   = temperature, time, pH, curing, mixing, deposition,
                            recycle/depolymerization process settings.
     TEST_METHOD         = measurement protocol family (cross-cut adhesion,
                            MEK double rub, salt spray, rain erosion).
     TEST_STANDARD       = exact ISO/ASTM/DIN/GB/JIS standard identifier.
     TEST_CONDITION      = substrate, exposure, panel, replicate position,
                            film thickness, scale definition, measurement
                            geometry, temperature, humidity.
     IDENTIFIER          = example/run/sample/formulation id.
     NON_DATA            = header, blank, separator, unit label, footnote marker,
                            "not measured" structural cell.

   Emit facts for RESULT_PROPERTY and FORMULATION_QUANTITY cells. For
   FORMULATION_QUANTITY facts, use the appropriate formulation property such
   as PROP_composition_weight_percent, PROP_formulation_component_mass,
   PROP_formulation_quantity, or propose a PROP_* if needed; bind the fact to
   the printed sample/formulation id (SB2, WB7, Example 1, Control, etc.) and
   put the material in resin_system/additives/monomer/solvent as appropriate.
   Attach FORMULATION_CONTEXT,
   PROCESS_CONDITION, TEST_METHOD, TEST_STANDARD, TEST_CONDITION, and IDENTIFIER
   cells as context on the related facts; do not count them as missing property
   facts. Also emit top-level cell_annotations so QA can see what was excluded
   from the coverage denominator.

   Performance rows such as "Surface (film)", "Surface (metal)",
   "Small flame test", "rating 1-6", "visual assessment", "corrosion rating",
   "adhesion class", "pass", "fail", "5B", "OK", and "n.d." are RESULT_PROPERTY
   when they are evaluation outputs. They MUST be extracted as property facts,
   even when the value is qualitative or an ordinal score.

   Rating scales are method-specific. Preserve the printed scale in
   result_value_text or test_condition. Do NOT normalize a bare "1-6" score
   unless the table/caption/paragraph states whether high or low is better.

1c. **Semantic coverage report.**
   In the top-level ``coverage`` object:
     - ``expected_result_cells`` counts RESULT_PROPERTY and FORMULATION_QUANTITY cells that should
       produce facts.
     - ``result_cells_extracted`` counts RESULT_PROPERTY and FORMULATION_QUANTITY cells represented by
       emitted facts.
     - FORMULATION_CONTEXT / PROCESS_CONDITION / TEST_CONDITION / IDENTIFIER /
       NON_DATA cells are excluded from the denominator and summarized in
       ``role_counts`` / ``notes``.
   If a table is mainly a formulation table, ingredient amounts are the L2
   facts. They are not optional context, because the KG/CSV must answer what
   each sample formulation contains.

1d. **Confidence rubric.**
   Use ``extraction_confidence`` as calibrated QA metadata, not a default
   self-approval score:
     >=0.95: value, property, row/column mapping, scale, and context are clear.
     0.85-0.94: value/property clear, with only minor missing context.
     0.70-0.84: OCR/header noise, inferred property label, or incomplete
                row-specific context.
     0.50-0.69: significant inference, no matched paragraph support, or
                uncertain method/scale.
     <0.50: candidate fact requiring review.

   Caps: no matched paragraphs -> <=0.85; OCR damage in row/column/property
   -> <=0.80; row-specific condition omitted -> <=0.80; only a subset of
   result rows extracted -> <=0.75; proposed canonical -> <=0.85 unless the
   source text makes the mapping obvious.

2. **Canonical IDs — propose-and-curate, NOT hard match.**
   The lists below are SEED REFERENCE, not a closed checklist. Pick the
   right ID for each slot using these priorities:

   (a) If a seed ID is a PRECISE semantic match → use it.
       e.g. "20° gloss" → ``PROP_gloss_20deg``  (use seed)

   (b) If the entity is REAL but no seed ID precisely matches → PROPOSE
       a new ID via ``proposed_canonicals`` AND use that proposed_id in
       the fact. The system routes proposed-ID facts to a curation queue
       where a human approves / rejects.
       e.g. "Defoamer" → propose ``MAT_defoamer_generic`` (sub_type=Additive)

   (c) NEVER stretch a seed ID to cover an entity it does not actually
       describe. Specifically:
       - DO NOT pick ``MAT_acrylic_resin`` for a defoamer / catalyst /
         wetting agent / matting agent. They are not acrylic resins.
       - DO NOT collapse two different specific components onto one
         seed ID just because the seed has nothing better
         (e.g. ``PAC1`` and ``PAC2`` are two distinct components — propose
         two separate IDs).
       - DO NOT add suffixes like ``_horizontal`` / ``_dry`` /
         ``_vertical`` to a seed ID. Position / direction info goes into
         ``evidence_pointer.column``.
       - Sample / formulation identifiers (``C1B1``, ``Example E4``,
         ``I1``) are NOT materials. They are sample names. Do not use
         them as ``resin_system``.

   (d) When proposing, follow the naming convention
       ``<TYPE>_<descriptor>_<lowercase_underscored>``.
       Pick a name SPECIFIC enough to disambiguate:
         "PAC1, an acrylic polyol" → ``MAT_PAC1_acrylic_polyol``
         "Cathoguard 800 electrocoat" → ``MAT_cathoguard_800_electrocoat``
         "DLT directional uniformity (h vs v)" → ``PROP_film_thickness_directional_uniformity``

   (e) ``confidence`` on a proposal:
         "high"   — the entity name is unambiguous and chemistry obvious
         "medium" — chemistry inferred from context
         "low"    — proposing because no fit exists, but unsure

   (f) **sub_type is a CLOSED enumeration. NEVER invent new sub_types.**
       The 7 MAT sub_types are:
         Resin / binder, Crosslinker / Curing agent, Pigment, Filler,
         Additive, Solvent, Monomer
       The 4 SUB sub_types are: Metal, Plastic, Mineral, (and we accept
       coatings on cementitious / mineral substrates as Mineral).
       The 4 APP sub_types are: Automotive, Industrial protective,
       Specialty, Architectural.

       If you encounter a material/substrate/application that doesn't
       cleanly map, pick the SEMANTICALLY CLOSEST existing sub_type using
       chemical / functional analogy. Examples (apply same reasoning to
       any unfamiliar entity):

         Material analogies:
           Dye / colorant         → Pigment       (both color the film)
           Surfactant / wetter    → Additive       (formulation auxiliary)
           Antifoam / defoamer    → Additive
           Wax / matting agent    → Additive
           Catalyst / initiator   → Additive
           Adhesion promoter      → Additive
           UV absorber, HALS      → Additive
           Coupling agent (silane) → Additive
           Plasticizer            → Additive
           Diluent / reactive solvent → Solvent
           Reactive monomer (HEMA, BA, etc.) → Monomer
           Oligomer / prepolymer  → Resin / binder
           Hardener (epoxy / amine) → Crosslinker / Curing agent
           Inorganic filler (CaCO3, talc, SiO2) → Filler

         Substrate analogies:
           Cotton / textile / paper → Plastic     (organic substrate)
           Wood                     → Plastic
           Concrete / cement / stone → Mineral
           Glass                    → Mineral

       ANTI-PATTERN: do NOT propose sub_type="Dye" / "Surfactant" /
       "Wax" / "Textile" — these are NOT in ALLOWED_SUB_TYPES, the
       pipeline will reject and your propose will land in the wrong CSV
       column. Always squeeze into one of the 7 / 4 / 4 buckets above.

3. ``source_section_type`` must match where ``result_value`` lives:
   TABLE row → TABLE; figure caption sentence → FIGURE_CAPTION_FOOTNOTE; etc.

4. ``additives`` is a JSON list. ``process`` is an ORDERED list.

5. Separate test method, standard, and condition.
   - ``test_method`` is the protocol family or canonical TEST_* when stated.
   - Standard numbers such as ISO 2409 / ASTM D3359 / DIN 55654 go into
     ``test_condition.standard_id`` in this v1-compatible schema.
   - Exposure time, film thickness, angle, scale definition, substrate panel,
     temperature and humidity go into ``test_condition``.
   If a result is clear but the method is not stated, leave ``test_method``
   absent/null; do not guess from the property name alone.

5b. **COMPOUND CELL RULE** (V1.2.5):
    If a cell contains BOTH a numeric value AND a qualitative descriptor
    in the same string (e.g., "7.91 Hazy", "5.30 Clear", "OK 4B"):
      → result_value = the numeric portion (e.g., 7.91)
      → result_value_text = the FULL original cell text (e.g., "7.91 Hazy")
      → emit ONE fact (qualitative info preserved in result_value_text)

    Examples:
      cell "7.91 Hazy"   → result_value=7.91, result_value_text="7.91 Hazy"
      cell "5.30 Clear"  → result_value=5.30, result_value_text="5.30 Clear"
      cell "OK 4B"       → result_value=null, result_value_text="OK 4B"
                            (no numeric — both are qualitative)
      cell "Pass 5/5"    → result_value=5.0, result_value_text="Pass 5/5"
                            (5/5 is the numeric; "Pass" is the qualitative
                             summary)

    DO NOT split into two facts. The compound cell describes ONE
    measurement with multiple representations.

5c. **EMPTY CELL RULE** (V1.2.5):
    If a row has empty cell across all measurement columns (e.g., a
    header row, separator row, or a row with no data):
      → DO NOT emit any fact for that row.
    Empty cells indicate non-data structure (decorative or organizational),
    not measurement. The pipeline will reject empty-cell facts as noise.

6. ``polarity_hint``: positive for inventive examples, negative for
   comparative examples, unknown otherwise.

7. **Unit-level vs per-fact fields — TOKEN BUDGET RULE.**
   Before emitting any fact, decide for EACH of these fields whether it is
   the same for every row in this unit:

       application / substrate / resin_system / additives /
       process / test_method / test_condition / example_id

   If a field is identical across all rows → put it ONCE in
   ``unit_context``, OMIT from each fact entirely (do NOT emit
   ``"resin_system": null`` — just leave the key out).
   If a field genuinely varies per row (typical in a formulation table
   where every row picks a different ingredient) → emit it on the fact,
   leave the corresponding ``unit_context`` field null.

   **OMIT-NULLS RULE**: Never emit ``"<field>": null`` on a fact. If you
   don't have a value for a field, just don't include the key. This alone
   saves ~30% of output bytes.

   WORKED EXAMPLES:
     • Property test table (e.g. 6 metrics × 3 columns × 2 polarities = 36
       cells, all on the SAME coated panel made from ONE formulation):
       ``unit_context`` carries application + substrate + resin_system +
       additives + process + test_condition; each fact only carries
       fact_id + property + polarity_hint + evidence_pointer + result_value
       + result_value_text + extraction_confidence + claimed_in_claims.
     • Formulation table (e.g. 12 ingredient rows × 2 columns = 24 cells,
       each row a different chemical): ``unit_context`` carries application
       only; each fact carries its own resin_system OR additives entry
       depending on which row it is.

   FAILURE MODE TO AVOID #1: repeating a 4-step process[] in every fact
   will blow the 8192-token output budget around fact #15. Already lost
   24/36 cells of one table this way.

   FAILURE MODE TO AVOID #2: emitting ``"resin_system": "MAT_X"`` and
   ``"additives": ["MAT_Y"]`` on every fact when the values are constant
   across the whole unit. Move them into ``unit_context``.

   FAILURE MODE TO AVOID #3: emitting all fields as explicit ``null``.
   Adds ~200 bytes per fact for zero information gain.

8. **example_id — emit the literal sample identifier per fact.**

   ``example_id`` is just the cleaned SAMPLE ID, with original prefix
   letters preserved. polarity stays in ``polarity_hint`` (single source).

   Output format: a short string OR null. Do NOT add any new prefix
   like "E_" / "C_" — keep the patent's own literal id.

     "Example 1"            → "E1"          (matches existing E\d format)
     "Comparative Example 2" → "C2"
     "Beispiel 3"           → "E3"
     "Vergleichsbeispiel 4" → "C4"
     "实施例 5"             → "E5"
     "对比例 6"             → "C6"
     "C1B1"                 → "C1"          (drop sub-code B1, keep main)
     "I1B1"                 → "I1"          (KEEP I — do not fold to E)
     "CC-A1B1 (inventive)"  → "A1B1"        (drop product-line prefix CC-,
                                              keep multi-char sample id)
     "PC-B3 (comparative)"  → "B3"
     "Run 5"                → "5"           (no semantic prefix, bare id ok)
     "Sample A-3"           → "A3"

   DISCRIMINATING RULE (apply when example pattern is ambiguous):

     • If id contains a HYPHEN: "PREFIX-SAMPLE_ID"
         → drop everything before the hyphen (it's a product-line code)
         → keep everything after the hyphen literally
         examples: CC-A1B1 → A1B1, PC-B3 → B3, Sample-A3 → A3

     • If id has NO hyphen and starts with [CIE]: "[CIE]<digits>[<letter><digits>]"
         → main = first letter + immediately following digits
         → sub-code = anything after that (a letter+digits group); drop it
         examples: C1B1 → C1, I1B1 → I1, C12B1 → C12,
                   I22A3 → I22 (main = I22, sub-code A3 dropped)

     • If id has NO hyphen and starts with multi-letter prefix
       (CC1B1 / MA1 / etc): treat the whole letter run as a product-line
       prefix and split at the first digit boundary, then apply the
       hyphenless rule to the remainder.
         examples: CC1B1 → 1, MA1 → 1 (these are usually generic product
                   codes; the digit suffix is the sample id)

   LADDER / SUB-STEP TABLES (tables nested under ONE parent example):
     If the unit caption identifies one parent example
     ("Neutralization Ladder Example 12") and rows are ladder steps:
       → all facts share example_id = "E12" (parent's id, not the step)
       → put example_id in ``unit_context.example_id`` ONCE (TOKEN BUDGET)

   BARE-NUMBER FALLBACK:
     row/col is just a digit → only use as example_id if VLM description
     or caption confirms an "Examples 1-N" framing. If silent, emit null.

   POLARITY:
     polarity_hint independently captures inventive (positive) /
     comparative (negative) / unknown. Don't try to encode polarity in
     example_id — Stage 9 joins the two. If I1 vs E1 are DIFFERENT
     samples in the same patent, keep both literal — they ARE different
     example_ids.

   NULL POLICY:
     Don't guess. If no signal links this cell to any example, emit null.
     Pipeline routes null-example facts to a review queue.

FEW-SHOT EXAMPLES (study these — they show the propose-vs-seed decision)
========================================================================

EXAMPLE A — seed ID fits precisely. USE seed.
  Table cell: "20° gloss after Amtec, Example E4: 78.4 GU"
  → property = "PROP_gloss_20deg"  (seed fits — DO NOT propose a variant)

EXAMPLE B — entity is more specific than any seed. PROPOSE new.
  Table row: "PAC1, an organic-solvent-borne acrylic polyol dispersion, 25.00 wt.-%"
  → propose: {{kind: "MAT", sub_type: "Resin / binder",
              proposed_id: "MAT_PAC1_acrylic_polyol_dispersion",
              canonical_name: "PAC1 — acrylic polyol dispersion",
              source_text: "PAC1 ... acrylic polyol dispersion 25.00 wt.-%",
              confidence: "high"}}
  → fact.resin_system = "MAT_PAC1_acrylic_polyol_dispersion"
  Why NOT use ``MAT_acrylic_resin``? Too generic — collapses PAC1, PAC2,
  and any other specific acrylic to the same ID. Loses information.

EXAMPLE C — entity belongs to a category but no seed exists. PROPOSE.
  Table row: "Defoamer, 0.05 wt.-%"
  → propose: {{kind: "MAT", sub_type: "Additive",
              proposed_id: "MAT_defoamer_generic",
              canonical_name: "defoamer (generic, unspecified chemistry)",
              source_text: "Defoamer 0.05",
              confidence: "medium"}}
  → fact.additives = ["MAT_defoamer_generic"]
  Why NOT use ``MAT_acrylic_resin``? A defoamer is not an acrylic resin
  — wrong category entirely.

EXAMPLE D — nested property tables (rowspan polarity + property sub-rows).
  Real BASF table layout:
